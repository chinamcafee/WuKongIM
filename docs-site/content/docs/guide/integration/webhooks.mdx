---
title: Webhook
description: 安全、幂等地消费消息和在线状态事件。
---

Webhook 把已提交消息、离线接收者和在线状态变化发送到一个业务 HTTP 端点。它适合触发业务异步处理，不是客户端消息同步机制。

## 启用

在 `wukongim.toml` 中配置：

```toml
[webhook]
http_addr = "https://events.example.com/wukongim"
focus_events = ["msg.notify", "msg.offline", "user.onlinestatus"]
queue_size = 1024
workers = 16
request_timeout = "5s"
retry_max_attempts = 3
outbox_dir = "./data/wukongim-single-node-data/webhook-outbox"
outbox_max_entries = 1000000
outbox_max_bytes = 4294967296
outbox_dispatch_batch_size = 100
outbox_retry_base_delay = "1s"
outbox_retry_max_delay = "5m"
outbox_delivered_retention = "168h"
```

服务端会把事件名放在查询参数中：

```text
POST https://events.example.com/wukongim?event=msg.notify
Content-Type: application/json
```

任意 HTTP 2xx 都视为成功。关键消息事件使用同一投递身份进行持久重试；连接错误、超时或非 2xx 响应会保存到后续重试，直到进入死信。

## 支持的事件

| 事件 | 请求体 | 用途 |
| --- | --- | --- |
| `msg.notify` | 已提交消息数组 | 业务审计、搜索索引、异步通知 |
| `msg.offline` | 一条消息及一批离线 UID | 离线推送候选计算 |
| `user.onlinestatus` | 兼容在线状态字符串数组 | 在线状态的异步业务投影 |

`msg.notify` 的代表性请求：

```json
[
  {
    "header": {"no_persist": 0, "red_dot": 1, "sync_once": 0},
    "setting": 0,
    "expire": 0,
    "message_id": 123456789,
    "message_idstr": "123456789",
    "client_msg_no": "order-20260730-0001",
    "message_seq": 42,
    "from_uid": "system",
    "channel_id": "u1001",
    "channel_type": 1,
    "timestamp": 1785398400,
    "payload": "eyJ2ZXJzaW9uIjoxLCJ0eXBlIjoib3JkZXJfdXBkYXRlIn0="
  }
]
```

JSON 中的 `payload` 是 Base64。`msg.offline` 在 UID 数量较小时使用 `to_uids`；达到压缩阈值时可能改为 `compress: "gzip"` 与 Base64 编码的 `compress_to_uids`，接收端必须支持两种形式。

## 可靠性边界

<Callout type="info" title="关键消息 Webhook 使用有界持久 Outbox">
  `msg.notify` 和 `msg.offline` 会在调度前同步写入节点本地 Pebble Outbox，可在进程重启后恢复，并在各次尝试中复用稳定的 `X-WK-Webhook-ID`。容量受记录数和逻辑字节数限制；耗尽重试后进入死信，只能显式、有界地重放。`user.onlinestatus` 仍使用有界、尽力而为的内存队列。任何 Webhook 结果都不会改变已经成功的 SENDACK 或持久追加。
</Callout>

推荐的接收端流程：

1. 验证网络来源和入口身份。
2. 限制请求体大小并解析 `event` 白名单。
3. 把原始事件与 `X-WK-Webhook-ID` 写入自己的持久化队列。
4. 持久化成功后尽快返回 HTTP 200。
5. 在后台执行业务逻辑，并用可重试状态机记录结果。

服务端提供的稳定 ID 是关键事件的首选幂等键。如果兼容接收端必须自行派生：

- `msg.notify`：`event + message_id`；
- `msg.offline`：`event + message_id + uid`，逐个接收者去重；
- `user.onlinestatus`：按用户和设备覆盖为最新状态，不依赖每次过渡都到达。

## 安全

HTTP Sender 会设置 `Content-Type: application/json` 以及关键投递的身份/尝试 Header，但**不会添加签名或共享密钥 Header**。生产环境必须在它之外建立可信边界：

- 使用 HTTPS；
- 优先使用私网、服务网格或出口代理；
- 在反向代理层使用 mTLS、固定出口身份或受控凭据；
- 对来源 IP 和请求速率做限制；
- 不把回调端点暴露为匿名公网写入口；
- 不在日志中记录完整敏感 Payload。

## 容量与失败处理

- `queue_size` 是在线状态事件内存队列的有界容量。
- `workers` 控制 Outbox 调度和在线状态发送并发。
- `outbox_max_entries` 与 `outbox_max_bytes` 限制关键持久任务容量。
- `outbox_dispatch_batch_size` 限制每次领取的到期记录数。
- `offline_uid_batch_size` 同时控制离线 UID 分块/压缩边界。
- `retry_max_attempts` 是进入死信前的持久总尝试次数。

接收端持续失败时，应先修复或隔离接收端，而不是无限增大 Outbox。恢复后检查积压/死信指标，只重放明确且有界的一组记录。
