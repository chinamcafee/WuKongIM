# v2 → v3 迁移候选版本审查

审查基线为 `ab1ced72450658ba85399b03293ac37c20278721`，工作分支为
`codex/v2-v3-migration`。初次审查包括 `git diff HEAD --` 的已跟踪差异和
`git ls-files --others --exclude-standard` 的新增文件，共 172 个文件；
该基线之后尚无分支提交。修复纳入同一候选版本，不修改原版 v2。

依据为根及适用的 AGENTS/FLOW、存储兼容规则、E2E 规则，以及
[已确认的迁移设计](../specs/2026-09-06-v2-to-v3-migration-design.md)。
依照 code-review 技能，Standards 与 Spec 由两个独立审查代理并行检查；
以下保留两个轴，不将其合并排序。此记录是本地代码审查，不是 GitHub Review Agent
结果，也不是生产切换或性能验收授权。

## Standards

初次审查发现 **1 项 P1**：`internal/infra/migrationv3/install.go` 将最高 4 MiB
封成不可拆分 proposal，而原生副本恢复默认只接收 1 MiB 页，违反有界恢复与
背压约束。复现中 64 条 32 KiB 消息成功导入，随后原生 1 MiB 恢复返回
`channel: backpressured`；把离线校验预算放大无法证明运行时可恢复。

修复包括：共享原生恢复预算和计费函数；预检与直接导入拒绝超限单条消息；
导入批次同时约束存储编码与传输计费；原生 donor 合并多个完整 proposal 时也
遵守双预算；离线校验使用同样预算，拒绝旧实现生成的不可恢复产物。
回归测试覆盖真实安装、原生 Fetch、传输编解码、空副本 Replace 和逐条读回，
另覆盖恰在边界附近的批次合并及大协议字段。

## Spec

初次审查发现 **2 项 P1、1 项 P2**：

1. **P1，全局插件业务被当作管理描述归档。** 原版 Send/PersistAfter 不要求用户
   绑定；持久化 Status 也不是运行时活跃状态的依据。与“业务兼容缺口必须阻止
   完成”的要求不符。修复后，全局 Methods 或非空 Config 均要求兼容映射，否则
   拒绝；纯名称/版本/配置模板才可归档。使用原版公开写入及读取生成的精确 KV
   覆盖全局方法、禁用标记、仅配置、纯描述，并检查错误不泄露配置。
2. **P1，关键源索引损坏被目标重建掩盖。** 初次实现跳过原始索引，删除 Device
   UID 索引后仍能得到 `offline_verified`，但原版已无法通过 GetDevice 查回凭据。
   修复后，预检及归档重建都核对原版业务 lookup 与主记录、原分片位置；使用
   磁盘工作空间进行双向比较。原版有意稀疏的管理索引只做结构检查；原版截断
   遗留且确实指向已不存在主行的惰性消息 ID/client 索引可以归档。sender 残留仅在
   同一 sender/channel 有更大的有效消息序号、最大值查询结果不变时允许归档；改变原版未读计算的残留及跨分片 ID 遮蔽不能视为等价。
3. **P2，缺少多节点间改变节点数的黑盒组合。** 原测试仅覆盖 1→1、1→3、3→1、
   3→3；现增加 3→5，并复用历史、凭据、新写入、幂等、重启和 Leader 故障后的
   读写断言，保持真实 CLI/服务进程及公开协议边界。
