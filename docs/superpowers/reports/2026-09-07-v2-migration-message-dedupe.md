## 明确的规则与边界

1. 最新按**同频道内原 MessageSeq 最大**判断，不按遍历顺序、MessageID 大小或客户端时间戳判断。
2. MessageID 在每份来源内全量比较；ClientMsgNo 按 `(channel ID, channel type, sender, nonempty ClientMsgNo)` 判断。发送者或编号为空时不参与此幂等去重，遵循原生 v3 的唯一性检查。不同发送者/频道之间不因编号相同而删除。
3. 三节点物理副本分别计算。真正转换时仍需先确定源权威副本；不会拿副本数量、消息数量或去重结果代替权威证明。
4. 两种规则同时适用，取候选删除集合的并集。若某条保留候选又被另一条规则淘汰，报告 unresolved，不自行复活更旧消息或沿链扩大合并。
5. 跨频道 MessageID 的频道序号不可比较，必须报告 unresolved。当前实际备份未出现该情形。
6. 完整原数据仍需归档。规划只输出消息身份与摘要，不输出消息正文或凭据，不创建 selected/PREPARED/转换封印。

## 序号决策仍待明确

原生 v3 要求频道历史从 1 连续递增：`pkg/db/message/compat.go` 的 `compatibilityRowsFromRecords` 会拒绝不连续的 record.Index，正常追加也要求从当前末尾的下一个序号开始。相关核心路径与原生基线 `ab1ced72450658ba85399b03293ac37c20278721` 比较无差异。本次没有为去重添加 v3 存储例外。

删除原 1093 而保留原 1094 会留下空号，因此不能同时完成“删除旧重复”和“保留全部原序号”。建议在迁移工具内对受影响频道按剩余消息原顺序重新编号，并同步映射会话已读位置、删除位置、CMD 游标及其他引用该消息序号的状态。该提案改变先前的序号保留要求，**尚未获准或实现**。后续还需验证客户端旧游标处理和逐项业务语义，不能仅改消息表数字。

源权威性的历史配置未决项、设备凭据冲突、协议字段及插件兼容等既有问题不因本次清单通过而解决。规划退出码 0 不代表 prepare、import、独立 v3 验收或切换通过。
