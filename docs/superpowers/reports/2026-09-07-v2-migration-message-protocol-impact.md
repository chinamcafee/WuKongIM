## 15 条流主消息的实际内容

从已封存的原始行重新取出 45 个物理副本，逐行对照本轮摘要：

- 共 15 个不同 MessageID，同一消息的三个副本字段摘要相同。
- 全部 `Setting=2`，即旧流标记开启。
- 10 条原始主消息正文为零字节；4 条为 39 字节；1 条为 108 字节。
- 保留这 15 条主消息，不会把已经获准排除的流分片内容重新合并进正文。
  本轮没有读取或恢复分片正文，也没有把空主消息替换成编造的内容。

因此“清空 StreamNo”本身并不等于转换成普通消息：流标记仍然存在。
若以后选择普通消息形式，还需明确批准该标记的转换及其业务影响。

## 原生行为复现

新增隔离测试 `TestNativeFollowerRoundTripLosesLegacyMessageFields`，
分别使用合成的 RedDot 消息与带 Setting=2/StreamNo 的消息：

1. 迁移工具按现有规则拒绝该消息。
2. 实验绕过迁移准入，仅向临时数据库直接写原有格式的完整消息行。
3. 原生数据库读取确实能返回 RedDot/StreamNo，写入和原有 version-1
   proposal 均成功。这不是迁移通过的证据。
4. 经原生 Channel `ReadLog` → `ApplyFollower` 写入另一临时数据库后，
   MessageID、序号、正文和 Setting 保留，但 RedDot 变为 false，StreamNo 为空。
5. 原生 Channel Message/Record DTO 也不承载这两个字段；历史 API 读取适配器
   只从其中设置 SyncOnce，没有补回历史 RedDot。

测试通过，证明不能以“底层列存在、写入成功”替代完整读取/复制兼容性验证。
这是存储适配器实验，不是一次新的真实集群故障恢复验收，也没有修改该路径。
原生历史冷启动恢复问题继续作为独立未解决事项。
