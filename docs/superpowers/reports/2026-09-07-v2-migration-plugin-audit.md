## 两版边界

原 v2 的插件配置/注册存储属于节点本身，PluginUser 则是用户绑定。
v3 已有原生 `plugin_binding` 表和节点配置 Store，可以作为迁移的目标结构，
但仅有结构不能认证运行行为。还需核对程序部署、启动配置、Receive 触发、
回复发送及目标节点配置分配。

原 v2 的同优先级选择取 UID 索引首先遇到的记录，且选择时不按运行状态/Receive
能力筛选；v3 先按启用、运行状态及 Receive 方法筛选，然后优先级降序、编号升序。
现场只有一个声明 Receive 的绑定，未观察到同优先级竞争，但一般迁移工具不能
因此宣称所有插件都兼容。两版 Receive 的过滤条件也必须在实际联调中覆盖。

同样大小的集群可以显式制定节点配置对应关系，保留全部三份名字；缩减节点数
不能保留三个独立节点配置的原位置。工具不能用“最新节点”或 Slot Leader 自动
合并，因为它们不是这类配置的全局权威。目标配置分配尚未确认。

## 代码及验证

`wkmigrate diagnose` 的 `plugin.business_mapping` 明细新增配置 JSON、模板、
方法、完整原字段及插件身份指纹，以及方法数/配置字段数。只输出指纹，不输出
身份原文或配置值。配置 JSON 规范化使用 `UseNumber`，避免大整数被 float64
舍入后误报一致；不同数值写法保守保留差异。

相关测试覆盖配置键顺序/空白、配置值变更、大整数差异、脱敏、真实原版生成的
插件原始 KV、诊断保持 blocked、无 PREPARED seal、流存储排除不绕过插件检查。
原生 v3 的 Receive、启动配置与绑定相关测试也已通过。这些测试使用合成数据，
不等于现场旧插件进程联调通过。

六个迁移相关包的完整单元测试通过（usecase 6.982 秒、v2 adapter 91.144 秒、
v3 adapter 11.114 秒，其余三个包无测试文件）；插件/诊断专项测试及四个原生
插件相关包的筛选测试通过。日志与本次输入摘要保存在同一私有证据目录。

本轮没有重跑耗时约 20 分钟的完整真实 prepare：业务插件映射仍未实现，原阻断
条件仍成立。metadata-28 的来源证明继续作为历史证据，不改写为本轮通过结果。
