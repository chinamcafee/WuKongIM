## 已实现

通用 v3 修复在独立 `codex/red-dot-preservation` 工作树开发，基线为
`223d1eba2f7228806cfd2842d86dd60f9c7583f4`，同样的代码补丁已接入迁移工作树。

- HTTP `header.red_dot` 原先未进入发送命令，现按请求保留。Gateway 原本已映射此位。
- 补齐 SendCommand → durable Message → Channel Message/Record → 已有
  FramerFlags 掩码 0x02，以及持久化读取、复制、恢复、普通历史 API 返回路径。
- 复用已有存储位。消息键、列、行编码、兼容消息格式、proposal/entry v1 摘要
  均未改变；未新增 v2 专用存储路径或调整 v3 序号/追加校验规则。
- Channel RPC 使用 v8，增加 RedDot，并保持旧 v3–v7 解码及 v7 原有字段布局。
  对会丢失 true 值的旧版本编码明确报错。Quorum Exchange 使用 v4，不回退 v3。
- 迁移工具不再把 RedDot 视为不兼容字段；其他未支持字段仍阻止完成。
  `dedupe-plan` 报告/工作空间身份升级为 v4 / `:dedupe-v4`，避免复用旧判断结果。

目标集群各节点必须统一使用修复版本，已有 v3 的升级需要停流量并一起升级。
源 v2 不需要修改、启动或升级。旧二进制能识别未改变的存储格式，但再次写入、
复制仍可能丢失该位，因此不能把回退旧二进制称为“保留 RedDot 的回退”。
此前已被旧 v3 清零的历史值不能凭空恢复，必须以原始来源为依据。

现有 v1 proposal 摘要不包含 RedDot，本次也没有改变其历史定义。
所以摘要相等不能单独证明该位相等；迁移验收仍须独立比较完整消息字段。
本次修复不改变 v3 未读计数算法，不处理 StreamNo 或 CMD sync 的其他字段。

## 验证结果

- API、节点 RPC、发送契约与运行时、集群适配器、Channel 全子树、Channel RPC、
  DB 全子树相关单元测试通过。
- 固定的原有格式消息载荷，覆盖 RedDot=false/true，经打开旧行、读日志、
  Exchange 编解码、ApplyFollower 或原生恢复后重开数据库，值保持一致；
  重读的兼容消息载荷逐字节一致。原有 v1 manifest 继续可用。
- 单节点集群和三节点集群从各入口发送 false/true，再从各入口读取历史通过；
  单节点集群关闭并重启后的历史读取也通过（独立工作树组合测试 14.383 秒）。
- 旧协议 true 值拒绝降级测试通过，旧 v7 的 allocator proof 和历史头字段布局测试通过。
- 整组测试第一次出现复制修复队列用例超时；单独复查及最终整组重跑均通过。

迁移工作树复测：迁移用例 7.636 秒、v3 适配器 9.236 秒、v2 适配器全包
104.177 秒，组合根/CLI 编译通过；同一集成场景 11.390 秒通过。

**三节点冷重启验收仍未通过。** 修复版本在 6 条已确认消息全部读取成功后，

`223d1eba2` 同样复现 6 → 5（其 RedDot 原本为 0），因此这是独立的原生
历史可见性问题。没有为本轮迁移调整其存储/恢复规则，没有把该场景记为通过。

保留的常规集成测试明确覆盖“单节点重启、三节点运行中跨节点读取”。
完整三节点重启探针及两份失败证据另行保存在私有目录，避免将已知失败
掩饰成 RedDot 验证通过。这个原生问题继续阻止最终迁移切换验收。
