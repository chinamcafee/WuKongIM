## Demo 修复与部署

- 默认使用已有 Web Token，登录不调用 `/user/token`。专用测试账号注册须显式勾选。
- 凭据只保存在当前标签页 sessionStorage；URL 不携带 UID / Token。刷新、
  重新同步和切换账号会重建 SDK 实例及消息、会话、游标状态。
- 有草稿时禁用重新同步并提供提示；不自动丢弃草稿。初版浏览器弹窗使自动化
  阻塞，关闭准确归属的测试标签页后改用此方式，最终禁用/恢复行为已验证。
- 修复历史前插时缺少稳定 key、消息类型及订单内容未随 props 更新造成的
  错位。修复前原 100 条历史仅 51 条显示匹配，修复后 100 条逐条匹配。

## 单节点故障未通过

暂停准确归属 deployment-57、client-59 的节点 3 容器，模拟进程无响应。
恢复脚本在暂停前已启动，最多暂停 75 秒；实际 52.277 秒后恢复。
没有停止整个集群、修改副本数或触碰其他项目。

故障前样本频道归属物理 Slot 3，其 Leader 为节点 3；暂停后观测到 Leader
切换到节点 2。但入口 `/readyz` 返回：

```text
write probe: cluster: route not ready: channel placement candidates 2 below replica count 3
```

Demo 未能在本次故障观察窗口内完成收发和重新同步。期间发送的消息最终序号
105，服务端时间戳紧邻节点恢复；不能把最终送达当作故障期间持续可用。
恢复后再发的 106 立即可见。未发现这四条测试消息丢失或重复。

代码定位到 `pkg/cluster/node_write_probe.go`：`ProbeWriteReady` 检查新频道
放置候选数必须达到完整副本数，成功后才更新数据面租约。本报告保留这条证据，
尚未完成对消息阻塞完整因果链的回归证明，也没有通过降低副本数或放宽存储
规则绕过失败。建议下一步独立复现三节点/三副本停一节点，区分已有频道的
多数派读写能力、新频道放置约束与全局 readiness / 数据面租约。

本次没有验证入口节点 1 故障时 Demo 自动切换 HTTP / WebSocket 地址；当前
部署只有一个公开 API 入口，该能力不能从存储 Leader 切换推导出来。
